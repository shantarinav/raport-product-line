# AGENTS.md

## Проект

Это репозиторий продуктовой линейки «Рапорт».

«Рапорт» — линейка легких фронтенд-дашбордов для анализа CSV/XLS/XLSX-файлов без бэкенда.

Слоган:

> Excel докладывает главное

## Текущий статус

Проект находится в стадии активной разработки и поддержки.

Все актуальные дашборды находятся в `src/` и переведены на единый стек:

- React;
- TypeScript;
- Tailwind CSS;
- shadcn/ui primitives;
- lucide-react.

Актуальные дашборды:

- `#/ssz` — качество оформления ССЗ;
- `#/tessa` — исполнительская дисциплина Tessa;
- `#/print` — контроль печати;
- `#/support` — SLA закрытых заявок техподдержки.

`legacy/` удален и больше не является источником правды. Новые задачи нельзя строить на ссылках к legacy-коду.

## Главный принцип разработки

Новые фичи и новые дашборды должны переиспользовать накопленную базу опыта проекта, а не создавать параллельную дизайн-систему или новый UX с нуля.

Обязательное правило:

> Все новые фичи должны переиспользовать существующие компоненты из `src/shared/ui/`. Создание новых базовых компонентов допускается только при крайней необходимости.

Если нужного компонента нет:

1. сначала проверь `src/shared/ui`;
2. затем проверь локальные компоненты существующих дашбордов в `src/features/*/components`;
3. если паттерн повторяется минимум в двух местах, выноси его в `src/shared/ui`;
4. новый локальный компонент создавай только для специфики конкретного дашборда.

## Архитектура

Текущая структура:

```txt
src/
  features/
    ssz/
    tessa/
    print/
    support/
    file-loader/
    report-detector/
  shared/
    lib/
    styles/
    ui/
  pages/
    landing/
```

Правила разделения:

- парсинг файла — отдельно от UI;
- нормализация данных — отдельно от UI;
- расчеты и агрегации — в `logic` / доменных модулях;
- React-компоненты — только отображение, состояние экрана и пользовательские действия;
- IndexedDB — только через `src/shared/lib/historyDB.ts`;
- сборка snapshot — через `src/shared/lib/snapshotBuilder.ts`.

Не смешивать JSX с тяжелой бизнес-логикой, парсингом или хранением данных.

## Единая загрузка отчетов

Главная страница `#/` — единая точка загрузки всех файлов.

Правила:

- дашборды не должны иметь собственные upload-формы;
- кнопка в дашбордах называется «Заменить отчет» и ведет на главную;
- тип отчета определяется на главной по содержимому файла, а не по имени;
- после определения отчет парсится и данные передаются нужному дашборду через текущий механизм pending data;
- если пользователь обновил страницу дашборда и данных нет, нужно вернуть его на главную с понятным статусом.

TopBar не должен превращаться в меню дашбордов.

## Роутинг и публикация

Приложение использует hash-routing.

Причина: статический сайт должен работать на любом домене и в любой папке без серверного fallback для маршрутов.

Правила:

- использовать маршруты вида `#/print`, `#/ssz`, `#/tessa`, `#/support`;
- не возвращать BrowserRouter с обычными URL-путями без отдельного согласования;
- production-сборка должна иметь относительные пути к ассетам;
- перед публикацией запускать `npm run check` и переносить содержимое `dist/`.

## Технологический стандарт интерфейса

Интерфейс должен использовать:

- **Tailwind CSS** — для стилей, сетки, отступов, состояний, адаптивности и цветовых токенов;
- **shadcn/ui** — для базовых UI-компонентов;
- **lucide-react** — для всех иконок.

Запрещено использовать:

- собственные SVG-иконки, если есть подходящая иконка в `lucide-react`;
- сторонние UI-kit библиотеки, кроме `shadcn/ui`;
- CSS-in-JS;
- inline styles;
- новые отдельные CSS-файлы под конкретный дашборд без необходимости;
- hardcoded-цвета внутри компонентов, если можно использовать Tailwind token или CSS variable.

Допустимо использовать CSS-файлы только для:

- общих CSS variables;
- базовых theme tokens;
- технических случаев, которые сложно или нецелесообразно выразить Tailwind-классами.

## Визуальный контракт

Действующий визуальный эталон — текущая реализация в `src/shared/ui`, `src/shared/styles/theme.css` и рабочих дашбордах.

Ключевые паттерны:

- `PageShell` для страницы;
- `DashboardHeader` для шапки;
- `MetricCard` для KPI;
- `SectionCard` / `ChartCard` для виджетов;
- `FilterPanel` для панели фильтров;
- `FilterStatusBar` для активных фильтров;
- `DashboardSwitch` для переключателей;
- `DataTable` для таблиц;
- `FileDropZone` для главной загрузки;
- `ErrorState` / empty-state паттерны для отсутствия данных.

Новые дашборды должны выглядеть как часть линейки «Рапорт», а не как отдельный продукт.

## Правила по иконкам

Все иконки брать только из `lucide-react`.

Не создавать собственные SVG-иконки и не копировать SVG вручную в компоненты.

Рекомендуемые иконки:

- `FileSpreadsheet` — CSV/XLS/XLSX, таблицы, файл отчета;
- `UploadCloud` — drag-and-drop загрузка;
- `ShieldCheck` — локальная обработка файла в браузере;
- `CheckCircle2` — успешное состояние;
- `AlertTriangle` — предупреждение;
- `CircleX` — ошибка;
- `SearchCheck` — определение типа отчета;
- `Gauge` — аналитика / дашборд;
- `Printer` — дашборд печати;
- `ClipboardCheck` — Tessa / исполнительская дисциплина;
- `ClipboardList` — ССЗ / задания;
- `Factory` — производственный контекст;
- `Filter` — фильтры;
- `RefreshCcw` — сброс фильтров;
- `Info` — пояснение.

Правила:

- использовать иконки сдержанно;
- иконка должна иметь смысловую функцию;
- не использовать иконки как декор;
- размер обычно 16–24 px;
- `strokeWidth={2}`;
- цвет задавать Tailwind-классами;
- для одинаковых смыслов использовать одинаковые иконки во всех дашбордах.

## Бизнес-логика

При визуальных правках запрещено менять без явного согласования:

- расчеты;
- агрегации;
- структуру входных данных;
- порядок обработки данных;
- состав виджетов;
- расположение и порядок виджетов;
- поведение виджетов;
- фильтры и их связи;
- значения по умолчанию;
- сортировки таблиц;
- сценарии взаимодействия пользователя.

Если нужно изменить бизнес-логику, сначала описать, что именно меняется и почему.

## Фильтры

Фильтры применяются автоматически, если в конкретном дашборде уже не задан другой паттерн.

Стандарт:

- панель фильтров размещается под шапкой, как в текущих дашбордах;
- активные фильтры показываются через `FilterStatusBar`;
- выбранные фильтры должны иметь возможность сброса через крестик, если такой паттерн уже используется в дашборде;
- даты в активных фильтрах показывать в формате `дд.мм.гггг`;
- календарные поля не должны позволять выбирать даты за пределами периода загруженного файла;
- autocomplete-фильтры должны позволять и выбрать из списка, и набрать значение вручную.

## Режимы «Руководитель / Аналитик»

Для дашбордов с большим количеством виджетов использовать два режима:

- **Руководитель** — компактный управленческий обзор, KPI, главный вывод, ключевые зоны внимания;
- **Аналитик** — полный набор срезов, таблиц, трендов и детальных виджетов.

Правила:

- режим сохранять локально в браузере;
- переключатель должен быть компактным и не занимать отдельную большую карточку;
- руководителю не показывать перегруженные тренды и вторичные таблицы без необходимости;
- аналитику оставлять полный инструментарий.

## Главный вывод

Для новых дашбордов желательно делать блок «Главный вывод».

Он должен:

- быть кратким;
- объяснять управленческий смысл показателей;
- показывать статус: норма / контроль / критично;
- указывать основную зону внимания;
- не дублировать длинные таблицы;
- использовать те же карточки, цвета и бейджи, что остальные дашборды.

## Локальная история и тренды

История хранится локально в IndexedDB через `src/shared/lib/historyDB.ts`.

Правила безопасности:

- не сохранять сырые логи;
- не сохранять ФИО, пользователей, названия документов и другие персональные данные;
- сохранять только агрегированные числовые KPI;
- не отправлять данные на сервер.

Правила snapshot:

- snapshots строятся в `src/shared/lib/snapshotBuilder.ts`;
- базовая гранулярность трендов — месяц;
- месяц считается пригодным для тренда, если покрытие не меньше 50%;
- если новый snapshot покрывает месяц больше или ровно настолько же, он перезаписывает старый;
- если новый snapshot покрывает месяц меньше, старый сохраняется;
- для Print месячные KPI считаются без печати в PDF (без `Microsoft Print to PDF`).

## Print

Дашборд Print чувствителен к бизнес-логике.

Обязательные правила:

- по умолчанию пользовательская аналитика и история должны исключать печать в PDF;
- PDF-принтер — `Microsoft Print to PDF`;
- зеленый цвет использовать только для позитивных оценок, не для отклонений;
- риск-бейджи и отклонения не должны выглядеть как «хороший» статус;
- KPI-дельты: снижение проблемных показателей — зеленым, рост — красным;
- режим «Руководитель» не должен перегружаться фильтрами документа и детальными трендами;
- тренды показывать в режиме «Аналитик».

## ССЗ

Правила ССЗ:

- цель контроля и доля по технологии считаются по текущей бизнес-логике;
- зона внимания не должна показывать тех, кто уже уложился в цель;
- в зоне внимания прогресс должен быть красным/желтым, не зеленым;
- отсечка для зоны внимания считается как `100 - целевая доля`;
- тренд технологии строится по месяцам и только по месяцам с покрытием не меньше 50%;
- режим «Руководитель» показывает ключевые срезы, режим «Аналитик» — полный набор.

## Tessa

Правила Tessa:

- главная загрузка только через `#/`;
- быстрый фокус должен иметь понятные статусы: «Все задания», просрочка, дедлайн;
- если выбранный дедлайн не дает исполнителей с застрявшими договорами, показывать понятную пустую строку без технической формулировки;
- фильтры должны позволять ручной ввод, как в ССЗ.

## Support

Правила Support:

- цель контроля не должна быть выше нормы 95%;
- статус SLA использовать единообразно: норма / контроль / критично;
- ссылки на внешние системы в номерах заявок не добавлять без отдельного согласования;
- виджет SLA по темам должен фильтровать по клику только по смысловому элементу, а не по всей строке, если это мешает восприятию;
- пояснения графиков должны быть управленчески понятными, а не техническими.

## Проверка

Перед завершением задач запускать:

```bash
npm run check
```

Минимум для небольших промежуточных правок:

```bash
npm run typecheck
```

Перед завершением сообщать:

- что изменено;
- какие файлы затронуты;
- как проверено;
- менялась ли бизнес-логика;
- какие риски остались.
