# AGENTS.md

## Проект

Это репозиторий продуктовой линейки «Рапорт».

«Рапорт» — линейка легких фронтенд-дашбордов для анализа CSV/XLS/XLSX-файлов.

Слоган:

> Excel докладывает главное

## Вариант миграции

Используется вариант миграции №2:

> Дашборд ССЗ является визуальным эталоном для всей линейки «Рапорт».

Нужно использовать стилистику ССЗ для остальных экранов:

- шрифтовое оформление;
- вид загрузочного экрана;
- оформление шапки дашбордов;
- оформление переключателей;
- статусная полоска фильтра;
- подход к использованию иконок;
- цветовое оформление;
- общий характер карточек, таблиц и графиков.

# Технологический стандарт интерфейса

При миграции интерфейс должен использовать:

- **Tailwind CSS** — для стилей, сетки, отступов, состояний, адаптивности и цветовых токенов.
- **shadcn/ui** — для базовых UI-компонентов.
- **lucide-react** — для всех иконок.

Запрещено использовать:

- собственные SVG-иконки, если есть подходящая иконка в `lucide-react`;
- сторонние UI-kit библиотеки, кроме `shadcn/ui`;
- CSS-in-JS;
- inline styles;
- новые отдельные CSS-файлы под конкретный дашборд без необходимости;
- hardcoded-цвета внутри компонентов, если можно использовать Tailwind token или CSS variable.

Допустимо использовать CSS-файлы только для:

- общих CSS variables;
- базовых theme tokens;
- временной изоляции legacy-стилей, например `.print-dashboard`;
- технических случаев, которые сложно или нецелесообразно выразить Tailwind-классами.

Все новые или обновленные UI-компоненты должны быть React-компонентами, стилизованными через Tailwind classes и, где уместно, построенными на shadcn/ui primitives.


# Правила по иконкам

Все иконки брать только из `lucide-react`.

Не создавать собственные SVG-иконки и не копировать SVG вручную в компоненты.

Рекомендуемые иконки:

- `FileSpreadsheet` — CSV/XLS/XLSX, таблицы, файл отчета;
- `UploadCloud` — drag-and-drop загрузка;
- `ShieldCheck` — локальная обработка файла в браузере;
- `CheckCircle2` — успешное состояние;
- `AlertTriangle` — предупреждение;
- `CircleX` — ошибка;
- `SearchCheck` — определение типа отчета;
- `Gauge` — аналитика / дашборд;
- `Printer` — дашборд печати;
- `ClipboardCheck` — Tessa / исполнительская дисциплина;
- `ClipboardList` — ССЗ / задания;
- `Factory` — производственный контекст;
- `Filter` — фильтры;
- `RefreshCcw` — сброс фильтров;
- `Info` — пояснение.

Правила:

- использовать иконки сдержанно;
- иконка должна иметь смысловую функцию;
- не использовать иконки как декор;
- размер обычно 16–24 px;
- `strokeWidth={2}`;
- цвет задавать Tailwind-классами;
- для одинаковых смыслов использовать одинаковые иконки во всех дашбордах.


## Главный принцип

Это не редизайн UX и не переписывание бизнес-логики.

Задача — применить визуальный язык ССЗ к другим дашбордам, сохранив:

- расчеты;
- агрегации;
- структуру входных данных;
- порядок обработки данных;
- состав виджетов;
- расположение виджетов;
- порядок виджетов;
- поведение виджетов;
- переключатели внутри виджетов;
- значения переключателей по умолчанию;
- вкладки, если они есть;
- фильтры;
- логику фильтрации;
- сортировки таблиц;
- сценарии взаимодействия пользователя.

## legacy/

```txt
legacy/
  ssz/
  tessa/
  print/
```

`legacy/ssz` — визуальный источник правды.  
`legacy/tessa` и `legacy/print` — источники правды по бизнес-логике.

Не изменять файлы в `legacy/`, если задача явно этого не требует.

## Что брать из ССЗ

Из `legacy/ssz` нужно извлечь:

- цвета;
- типографику;
- размеры и веса шрифтов;
- Tailwind-паттерны, если они уже используются;
- отступы;
- скругления;
- тени;
- оформление карточек;
- оформление шапки дашборда;
- оформление загрузочного экрана;
- оформление переключателей;
- оформление фильтров;
- оформление статусной полоски фильтра;
- подход к иконкам;
- стили таблиц;
- стили графиков.

Не придумывать новую дизайн-систему, пока не проанализирован ССЗ.

## shadcn/ui

Для базовых компонентов использовать shadcn/ui.

Предпочтительные компоненты:

- `Card`, `CardHeader`, `CardTitle`, `CardDescription`, `CardContent`;
- `Button`;
- `Badge`;
- `Alert`, `AlertTitle`, `AlertDescription`;
- `Progress`;
- `Separator`;
- `Tabs`, если существующий UX уже использует вкладки или режимы;
- `Tooltip`;
- `Input`;
- `Select`;
- `Table`;
- `Switch`;
- `ToggleGroup`, если нужно сохранить существующий переключатель режимов;
- `DropdownMenu`, если он уже нужен существующему UX;
- `Popover`, `Command`, если они нужны для существующих фильтров.

Если существующий виджет имеет особое поведение, shadcn/ui использовать как базовую оболочку, но бизнес-логику не менять.

## TopBar

В `TopBar` должна быть только ссылка на главную страницу `/`.

Не добавлять ссылки на:

- `/tessa`;
- `/print`;
- `/ssz`;
- любые другие дашборды.

## Фильтры

Фильтры не перерабатывать.

Существующие фильтры нужно только визуально привести к стилю ССЗ, используя Tailwind и, где уместно, shadcn/ui (`Select`, `Input`, `Button`, `Badge`, `Separator`, `Popover`, `Command`).

Запрещено менять:

- состав фильтров;
- расположение блока фильтров;
- порядок фильтров;
- названия фильтров без отдельного согласования;
- доступные значения;
- значения по умолчанию;
- логику применения;
- взаимосвязь фильтров;
- поведение кнопки сброса;
- поведение при пустом результате.

## Виджеты и переключатели

Если в виджете есть переключатель, он должен остаться.

Можно изменить только внешний вид переключателя под стиль ССЗ, используя Tailwind и shadcn/ui (`Switch`, `ToggleGroup`, `Tabs` — только если это соответствует текущему поведению).

Запрещено менять:

- наличие переключателя;
- место переключателя;
- поведение переключателя;
- значение переключателя по умолчанию;
- варианты переключения;
- данные, которые показывает виджет в каждом режиме.

## `/print`

Дашборд `/print` особенно чувствителен.

При миграции `/print` сохранить:

- расчеты;
- структуру данных;
- поля;
- агрегации;
- существующие проверки;
- расположение виджетов;
- порядок виджетов;
- поведение виджетов;
- переключатели;
- вкладки;
- фильтры и их поведение;
- сортировки и режимы таблиц.

Старый CSS `/print` временно изолировать через `.print-dashboard`.

`/print` должен выглядеть как часть линейки в стиле ССЗ, но не должен менять бизнес-логику и UX.

## Проверка

После изменений запускать:

```bash
npm run build
```

Если в проекте есть тесты или линтеры, запускать их также.

Перед завершением задачи сообщать:

- что изменено;
- какие файлы затронуты;
- как проверено;
- какие элементы стиля взяты из ССЗ;
- какие компоненты shadcn/ui использованы;
- какие иконки lucide-react использованы;
- не изменялась ли бизнес-логика;
- какие риски остались.
