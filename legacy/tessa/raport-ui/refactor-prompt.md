# Задача для Codex: привести существующий дашборд к бренду «Рапорт»

## Важное правило: сначала осмысление, потом переделка

Перед тем как менять код, используй установленный skill `brainstorming`.

Цель — не механически натянуть брендбук, а вдумчиво определить, как лучше представить данные пользователю.

Брендбук «Рапорт» — это не жесткая сетка, а система визуальных и UX-принципов. Приоритет — удобство понимания данных пользователем.

Если стандартная компоновка ухудшает восприятие данных, выбери другую компоновку, но сохрани стиль, язык, цветовую систему и обязательные элементы бренда.

Перед изменением кода подготовь короткий план:

1. Что является главным вопросом дашборда.
2. Кто основной пользователь.
3. Какие блоки стоит оставить.
4. Какие блоки стоит изменить.
5. Какую компоновку ты выбираешь и почему.
6. Где ты отступаешь от стандартного шаблона «Рапорта» и зачем.
7. Какие риски есть при переделке.

Только после этого приступай к изменению кода.

Используй дополнительный файл:

- `raport-ui/brainstorming-before-refactor.md`

## Бренд

Название линейки: **Рапорт**  
Слоган: **Excel докладывает главное**

«Рапорт» — это быстрый одностраничный дашборд из Excel-файла. Пользователь загружает Excel и получает на одном экране ключевые показатели, графики, проблемные зоны и понятный цифровой доклад.

Важно: не перегружай интерфейс стилистикой «советского завода». Название задает характер, но визуально продукт должен оставаться современным, чистым и деловым.

## Что нужно сделать

1. Переименовать дашборд в формате **Рапорт: [тема дашборда]**.
2. Добавить в верхнюю часть страницы название, слоган, краткое описание, компактный блок текущего файла и кнопку «Заменить файл».
3. Сохранить существующую бизнес-логику и не ломать расчеты.
4. Переделать визуальный стиль по цветовой системе бренда.
5. Добавить или адаптировать блок загрузки Excel.
6. Привести фильтры к стандарту бренда с учетом пользы для пользователя.
7. Привести KPI к единому виду.
8. Добавить блок автоматических выводов, если он полезен и его можно построить корректно.
9. Привести тексты интерфейса к русскому языку.
10. Использовать классы с префиксом `raport-` для новых элементов.

## Правила структуры и нейминга виджетов

1. Сначала определить главный показатель дашборда. Все остальные показатели считать вспомогательными.
2. Верхние KPI должны показывать только действительно главные показатели. Не добавлять KPI ради заполнения места.
3. Если несколько виджетов показывают одну и ту же метрику по разным объектам, не повторять метрику в каждом заголовке. Лучше:
   - раздел: «Срезы по технологии»;
   - подзаголовок раздела: «Доля работ по технологии по заказам, цехам, мастерам и операциям»;
   - виджеты: «Заказы», «Цеха», «Мастера», «Операции».
4. Названия лидербордов должны объяснять управленческий смысл, а не только объект:
   - «Лидеры по технологии» — положительный рейтинг;
   - «Зона внимания» — рейтинг, где нужен управленческий фокус.
5. Подзаголовки лидербордов должны уточнять объект анализа: «Мастера, достигшие целевой доли...» или «Мастера с наибольшим объемом работ...».
6. Не использовать обвиняющий язык в названиях блоков. Вместо «лузеры», «плохие», «красная зона» использовать «Зона внимания», «Ниже цели», «Требует проверки».

## Правила расчетов и подписей

1. Не менять бизнес-логику расчетов без отдельного решения пользователя.
2. Разделять:
   - локальную долю объекта: часть внутри собственных работ объекта;
   - вклад в проблему: часть объекта в общем объеме проблемы.
3. Не подписывать вклад в проблему как «доля без технологии». Если показывается вклад, так и писать: «вклад в работы без технологии».
4. Если под шкалой уже есть крупный процент, не дублировать его в подписи.
5. Под шкалой лучше показывать масштаб:
   - `н-ч всего`;
   - `н-ч · опер. по тех.`;
   - при необходимости `н-ч · опер. без тех.` для проблемного блока.
6. Для позитивных лидербордов сортировка должна учитывать управленческий вес: сначала объем по ключевой метрике, затем количество операций, затем процент.
7. Для проблемных лидербордов сортировать по объему проблемы: нормо-часы без технологии, затем операции без технологии, затем худшая доля.
8. Малые выборки нельзя поднимать в рейтинг только из-за красивого процента. Если малые объемы важны, показывать их статусом или понижать приоритет в сортировке.

## Фильтры

1. Фильтры должны применяться ко всем виджетам, где это логически возможно.
2. Связанные фильтры должны ограничивать друг друга:
   - выбран цех → доступны только мастера и заказы этого цеха;
   - выбран мастер → доступны только его цеха и заказы;
   - выбран заказ → доступны только релевантные комплекты, цеха и мастера.
3. Активные фильтры нужно показывать плашками. Начальное состояние тоже должно выглядеть как набор плашек, а не как обычный текст.
4. Если фильтры применяются автоматически, не добавлять кнопку «Применить».
5. Кнопку «Сбросить фильтры» делать вторичной: она не должна конкурировать с основными действиями.

## Подготовка к публикации

1. Перед сборкой удалить или не копировать неиспользуемые ассеты.
2. Сжать PNG-иконки и логотипы до фактических размеров использования. Иконка 20 px не должна весить мегабайты.
3. Проверить, что сборка использует относительные пути к `assets`, если дашборд может публиковаться в подпапке.
4. После сборки сделать архив, внутри которого `index.html` и `assets/` лежат сразу в корне.
5. Перед выдачей архива прогнать тесты и production-сборку.

## Разрешенные отступления от шаблона

Можно отступать от стандартной структуры брендбука, если это улучшает удобство анализа и восприятие информации.

Разрешается:

- менять порядок блоков;
- увеличивать главный график;
- делать таблицу главным элементом страницы;
- переносить KPI ниже, если они вторичны;
- объединять несколько KPI в один блок;
- скрывать второстепенные блоки в раскрывающиеся секции;
- использовать вкладки;
- использовать горизонтальные фильтры вместо боковой панели, если так удобнее;
- использовать боковую панель даже при небольшом количестве фильтров, если фильтры сложные;
- заменить тип графика;
- отказаться от блока автоматических выводов, если выводы невозможно построить корректно по данным.

Нельзя отступать от следующих правил:

- название должно быть в формате «Рапорт: [тема]»;
- слоган «Excel докладывает главное» должен присутствовать;
- пользователь должен видеть, какой Excel-файл загружен;
- должна быть возможность заменить файл в процессе работы;
- цвета должны использоваться по смыслу;
- красный только для критичных отклонений;
- интерфейс должен быть на русском языке;
- бизнес-логика расчетов не должна быть сломана;
- данные не должны сохраняться на сервере без отдельного требования.

## Важные ограничения

- Не переписывай проект полностью, если это не требуется.
- Не ломай существующую обработку Excel.
- Не меняй бизнес-смысл показателей.
- Не добавляй серверную часть.
- Не сохраняй данные на сервере.
- Все должно работать в браузере, как и раньше.
